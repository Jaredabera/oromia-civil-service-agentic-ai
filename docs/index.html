Architecture built around trust

Autonomy is useful when the model can interpret goals, inspect UI state, act within controlled boundaries, recover from uncertainty, and leave verifiable evidence of its actions.

Human-in-the-loop

Observe → Act → Verify

The browser agent is a controlled execution system—not a direct model-to-keyboard bridge.

GOAL Process Afaan Oromoo application | OBSERVE Read document / portal state | PLAN Choose constrained next action | ACT Click, type, select or wait | VERIFY Read-back values & policy checks | HUMAN GATE Claim, correct, approve | RECEIPT Confirm authorized submission

Recovery is part of the design

Unexpected labels, missing fields, latency spikes, model formatting failures, and uncertain identity data should lead to bounded retries, durable checkpoints, or supervisor escalation—not silent submission.

An agent's self-reported confidence is not a guarantee of correctness. Extraction and action reliability must be measured on relevant validation data.

Security, reliability and accountability

A credible government pilot requires controls that are tested rather than simply declared.

Data protection

Keep identities, document images and screenshots off the public website. Enforce data minimization, role-scoped access, and deletion policies.

Action governance

Authenticate operators, validate approved field digests, constrain browser destinations, and verify that every submission is authorized.

Evaluation

Measure extraction accuracy, task success, intervention rates, incident frequency, latency and throughput on an audited benchmark.

Research milestones

Demonstrated prototype scope

Local FastAPI workflows, Chromium mock-portal automation, field verification, synthetic cases, human approval gates and error logging. Previous V3 builds required a hidden-input approval-token fix.

Future deployment evidence
